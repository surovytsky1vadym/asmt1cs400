What I understood
-----------------
Well, I see a compiler runs in four stages: at first, emoji bytes are turned into tokens by lexer, 
then parser builds an AST from them, then semantic part checks the program, and after all of that LLVM IR is generated.
The .ll file is the only output and clang turns it into a program.
Variables written at the top level as globals, obviously, i32 can turn into i64 by itself, but not vice-versa, since the data might not fit.
Magic wand is a func with typed parameters and a result type, while checkered flag is used to return, so, basically, every path in a function has to end with this.
There are no void functions, everyone returns something.
There is also a semantic pass, which checks the whole program before any code is made, variables names must be declared first, before they are used.
So, also, there is a crate structure, with constants as castles and gamepads as mutables. We create objects with *new* emoji, and get to fields through chains, like it is shown in readme: we create a mutable c with circle type and get to y afterwards with c.center.y, which means in a circle "c" lets grab a center and move it to "y" coordinate.

      🏁 x ✖️ x ➕ y ✖️ y ⚔️
    🏟️

    🪄 shift(dy 🔫 💎32) ➡️ 💎32 🏟️       // assigns a field → mutating

  New EBNF rules

  The rules marked changed replace their Stage 1 versions. Each change only adds
  alternatives, so every Stage 1 program still parses.

  (* ── Program (changed): declarations may appear only at the top level ── *)
  program        = { topItem } ;
  topItem        = funcDecl | structDecl | statement ;

  (* ── Functions ───────────────────────────────────────────────────────── *)
  (* 🪄 name ( params ) ➡️ resultType 🏟️ body 🏟️                           *)
  funcDecl       = "🪄" , identifier , "(" , [ paramList ] , ")" ,
                   "➡️" , typeName , "🏟️" , stmtBlock , "🏟️" ;
  paramList      = param , { "," , param } ;
  param          = identifier , "🔫" , typeName ;          (* params are 
  constant *)

  returnStmt     = "🏁" , expr , "⚔️" ;                    (* leave with a value
  *)

  (* ── Structures ──────────────────────────────────────────────────────── *)
  structDecl     = "📦" , identifier , "🏟️" , { structMember } , "🏟️" ;
  structMember   = fieldDecl | funcDecl ;                  (* funcDecl = member 
  function *)
  fieldDecl      = ( "🎮" | "🏰" ) , identifier , "🔫" , typeName , "⚔️" ;
                   (* 🎮 mutable field, 🏰 constant field; no initializer *)

  (* ── Types (changed): a structure name is a type ─────────────────────── *)
  typeName       = "💎32" | "💎64" | "🛡️" | identifier ;

  (* ── Statements (changed) ────────────────────────────────────────────── *)
  statement      = varDecl | constDecl | identStatement | ifStmt
                 | printStmt | overflowCheck | returnStmt ;

  (* Replaces Stage 1 "assignment". The parser reads a postfix chain, then
     decides: if a 🎯 follows, the chain must be an lvalue; otherwise it must
     end in a call. A bare identifier is an lvalue, so "x 🎯 1 ⚔️" stays valid. 
  *)
  identStatement = assignment | callStmt ;
  assignment     = lvalue , "🎯" , expr , "⚔️" ;
  lvalue         = identifier , { "." , identifier } ;     (* x  |  c.center.x 
  *)
  callStmt       = postfix , "⚔️" ;                         (* postfix must end 
  in a call *)

  (* Print (changed): one or more items, then one newline *)
  printStmt      = "📢" , printItem , { "," , printItem } , "⚔️" ;
  printItem      = stringLiteral | expr ;

  (* ── Expressions (changed below unaryExpr) ───────────────────────────── *)
  unaryExpr      = [ unaryOp ] , postfix ;                 (* was: primary *)

  postfix        = primary , { "." , identifier , [ callArgs ] } ;
                   (* ".f" = field access, ".m(...)" = member call; chains nest 
  *)

  primary        = intLiteral
                 | boolLiteral
                 | identifier , [ callArgs ]               (* variable | 
  function call *)
                 | "🆕" , identifier , callArgs            (* object 
  construction *)
                 | "📥" , "(" , ")"                        (* read one integer 
  *)
                 | "(" , expr , ")" ;

  callArgs       = "(" , [ expr , { "," , expr } ] , ")" ;

  (* ── Lexical rules (new tokens) ──────────────────────────────────────── *)
  (* Emoji keywords/operators, matched as exact UTF-8 byte sequences,
     longest match first (same mechanism as Stage 1):
       🪄  U+1FA84          KW_SPELL   function / member function
       🏁  U+1F3C1          KW_FINISH  return
       📦  U+1F4E6          KW_CRATE   structure
       🆕  U+1F195          KW_NEW     object construction
       📥  U+1F4E5          KW_READ    read integer from stdin
       ➡️  U+27A1 U+FE0F    OP_ARROW   result type                          *)
  comma          = "," ;
  dot            = "." ;
  stringLiteral  = '"' , { stringChar | escape } , '"' ;   (* one line only *)
  stringChar     = any_char - ( '"' | "\" | newline ) ;
  escape         = "\" , ( "n" | "t" | '"' | "\" ) ;

  Choices you may want to change

  1. Construction uses 🆕 Point(...) with a keyword, not Point(...). With the
     keyword, the parser and --ast can tell construction (New) from a function
     call (Call) without asking the semantic pass. Values are positional, in
     field-declaration order.
  2. The postfix chain is one AST node. c.center.move(1) becomes
     Chain(ends_in_member_call=True) holding a base and a list of steps. The
     spec asks --ast to show whether a chain ends in a member call, and this
     flag covers that directly.
  3. Assignment targets are restricted in the grammar. lvalue allows fields
     only, so a.f().x 🎯 1 is a syntax error. The mutability of each step is
     checked later, in the semantic pass.
  4. 📢 takes several items and prints one newline at the end, with no separator
     between items. This answers the spec's "where print puts a newline"
     question.
  5. Every function must have a result type. There are no void functions, and a
     mutating member like shift still returns a value. This keeps the rules
     simpler, but it means writing a dummy 🏁 in such members. I can add a void
     form if you'd rather avoid that.
  6. 📥() keeps its parentheses so it reads like a call, matching the course's
     read(). It would also parse without them.

          + before any code is generated. The first rule that is broken i
          +s reported as `compilation error: line L:C: message`. Each rul
          +e below names a program that follows it (`tests/run/` or `test

      197 +| 1 | A variable must be declared before it is used: a name is
          + visible from the statement after its declaration. | `run/read
          +_sum` | `undeclared_variable` |                               
      198 +| 2 | A scope is the top level, a function body (together with
          + its parameters), or one `🐉` / `👻` block. A name can be decl
          +ared only once per scope. An inner block may declare a name th
          +at already exists outside; the inner declaration hides the out
          +er one until the block ends. | `run/scopes_shadowing` | `redec
          +lared_variable` |

          +eclared_below` |

⏺ Your opening paragraph has the four stages right. One correction before you
  build on it: llvmlite isn't generated. It's the library the compiler uses to
  build the LLVM IR, and the IR is the only output. "turnedd" is also a typo.

  Below is the reasoning behind each decision and where to see it in the code.
  I've left the conclusions for you to draw, and I haven't changed the file.

  1. A function sees only globals declared above it

  Top-level statements run in order, as the program's main. Top-level variables
  become LLVM globals (kagu.global.<name>) so that functions can reach them.
  Each global starts at zero and gets its real value when its declaration line
  runs.

  The semantic pass takes a snapshot of the global names at the moment it
  reaches a function's declaration. Look at dict(self.global_scope.names) in
  _check_function in kagu/semantic.py. That snapshot is the only set of globals
  the body can see.

  Why: it keeps "declare before use" meaningful for functions too.

  Edge case: a function can be called before the global it reads has been
  initialized, because calls can come earlier in the file than the function. In
  that case it reads 0.

  2. i32 widens to i64 automatically, never the reverse

  Widening can't lose information, but narrowing can, so only widening is
  implicit. Two places implement it:
  - _assignable in semantic.py decides when it's allowed.
  - _widen in codegen.py emits it as sext (sign extend), which keeps negative
    numbers negative.

  Integer literals take the smallest type they fit in, which is why 2147483648
  can't go into a 💎32. There is no cast operator: 💥 only checks a value, it
  doesn't convert it.

  3. Runtime errors go to stderr with exit code 1

  + - * use LLVM's llvm.sadd.with.overflow family. These return a pair: the
  result and a flag saying "it overflowed". The generated code branches on that
  flag. On overflow it calls one shared helper, kagu.rt.fail, which writes the
  message to file descriptor 2 (stderr) with dprintf and then calls exit(1).

  Why stderr: the program's real output on stdout stays clean, so tests can
  compare it exactly. The exit code tells the shell or test runner that the
  program failed. Output printed before the error still appears, because exit
  flushes the buffer.

  4. Objects print as Point(x: 3, y: 4)

  The spec asks for "its type and its fields". The code that prints an object
  (_print_struct) never mentions a specific structure. It loops over the field
  table from the semantic pass and does three things per field:
  1. A gep (get element pointer) by the field's index, to get the field's
     address.
  2. A load, to read the value.
  3. A printf with a format picked by the field's type.

  A field that is itself a structure is printed by calling the same function
  again. That's why a new structure prints correctly without any new compiler
  code.

  5. 📥() gives 0 when there's no input

  The generated code stores 0 into the slot first, then calls scanf("%d", slot).
  If scanf can't read a number, it leaves the slot untouched, so the result is
  0. Reporting an error would also have been reasonable; this was simply the
  more predictable choice. 📥() always has type i32.

  Two parts worth understanding before you write

  - Mutating member functions. A member is mutating if it assigns a field, or
    calls another mutating member on its own object. That second part depends on
    other members, so the checker loops until nothing changes
    (_resolve_mutating_members). To see it, try making tickTwice in
    tests/run/member_mutation.txt callable on a 🏰 object.
  - The entry / body blocks. The first codegen version produced IR that clang
    rejected. All stack slots (allocas) now go in a separate entry block, which
    jumps to body. Compare any function in a generated .ll file against _begin
    in codegen.py and you'll see the split.
